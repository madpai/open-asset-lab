# Source NPC architecture: conceptual lessons

**VERIFIED from [Valve's SDK `ai_basenpc.h`](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/server/ai_basenpc.h):** NPC thinking gathers conditions, selects a schedule, runs tasks, can interrupt a schedule when a condition changes, and can choose a failure schedule. The SDK separates senses, navigation and behaviors; [navigator API](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/server/ai_navigator.h) exposes path and movement concerns. These are *roles* worth preserving, not a class layout to port. The shipped Source 1 SDK is a partial, game-specific codebase and its [license](https://github.com/ValveSoftware/source-sdk-2013/blob/master/LICENSE) is unsuitable as a general MegaMod implementation donor.

| Source concept | Evidence | MegaMod interpretation |
|---|---|---|
| conditions / schedule / tasks | [`ai_basenpc.h`](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/server/ai_basenpc.h), [`ai_basenpc_schedule.cpp`](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/server/ai_basenpc_schedule.cpp) | Explicit observation, chosen goal and cancellable executor. |
| senses and enemy memory | base NPC references `CAI_Senses` and enemy-memory updates in [`ai_basenpc.cpp`](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/server/ai_basenpc.cpp) | Separate presently seen from remembered target and last position. |
| navigator | [`ai_navigator.h`](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/server/ai_navigator.h) | Path failure, movement and task failure are distinct. |
| behavior extensions | [`ai_behavior.h`](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/server/ai_behavior.h) | Optional reusable decision modules, not a mandatory inheritance tree. |
| relationships and debug | [`ai_concommands.cpp`](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/server/ai_concommands.cpp), [`baseentity.h`](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/server/baseentity.h) | Inspect relationship state, LOS blockers, name, bounds and current reason. |

**Reusable patterns:** a decision is an interruptible task with explicit success/failure; conditions are cached observations, not arbitrary polling inside each action; a target's last known position differs from a currently visible target; a navigator returns status rather than teleporting the body; scripted sequences need a controlled temporary claim on agent control; debug overlays expose current schedule, task, conditions and route. Hint nodes and authored positions show why spatial semantics often need designer input even when pathfinding is automatic.

**Source I/O:** the locally installed Garry's Mod FGDs declare target names, input/output signatures, NPC relationship authoring, hint/assault points and scripted activities. Source's event wiring aged well as a creator affordance because map authors can inspect it. Its dynamic name targeting and numerous special-case classes are poor fits for MegaMod's X4 load-resolved typed references. Source's save/restore tables and client/server entity split show that durable state and visual state must be explicit, but this study did not validate a full save-game migration design. [MegaMod's own world entity contract](https://github.com/madpai/megamod-showdown/blob/2eae9df/docs/WORLD_ENTITIES.md) is the implementation baseline.

**Avoid:** copying the large inheritance hierarchy, numerous hard-coded condition/task enums, map-class exceptions, or implicit entity-name lookup during play. Source's target naming and entity I/O are useful authoring precedents, but MegaMod already resolves typed references at load and uses a bounded event queue. Extend those guarantees for AI. For doors, triggers and movers, the NPC should use the same world input/action as a player, script or X7 condition/action graph. Navigation should only establish *where to stand and whether traversal is possible*.

**Source 2 boundary:** the [Valve Developer Community's Source 2 `phys_spring` entity page](https://developer.valvesoftware.com/wiki/Phys_spring_%28Source_2%29) still documents target names and typed inputs. That is narrow evidence that entity I/O remains an authoring concept in at least one Source 2 entity. This study did not inspect a Source 2 SDK or establish Source 2 NPC, navigation or animation internals. Its tools and compiled content need separate research; do not project Source 1 schedules onto it.
