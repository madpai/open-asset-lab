# Goal-oriented action planning

**VERIFIED from Jeff Orkin's [F.E.A.R. technical account](https://www.gamedevs.org/uploads/three-states-plan-ai-of-fear.pdf):** planning searches a symbolic world-state/action graph; actions have preconditions and effects, can include procedural tests, and carry costs. The goal is to derive a sequence of feasible actions rather than author every transition. It is a planning layer, not a replacement for navigation, animation or execution. The paper is published architectural evidence; F.E.A.R.'s proprietary implementation is not a code source.

For MegaMod, the illustrative plan `reach control_room` might require `door_open`, achieved by `use(button)` after `move_to(button)`. To be valid, each symbolic effect must correspond to a real engine event and be checked after execution. A failed use, locked door or moved target invalidates the plan. Dynamic preconditions like reachability can be expensive; cache or evaluate carefully. The planner must bound states, depth, time and candidate objects, and report whether a plan was complete, partial or impossible. With many entities and freely combinable actions, the search space expands quickly.

**When it helps:** systemic worlds with many changing object combinations where authored sequences explode. **When it hurts:** a small combat/patrol loop whose reactions are clearer as fixed tasks or a BT. A planner can choose one short plan, while a simple executor runs one action at a time through X7/general engine actions. Replan on meaningful world changes or action failures; do not search every frame. Record expanded nodes and rejected preconditions for debugging.

**Recommendation:** defer GOAP until X7 action semantics, affordances and failure results are proven across multiple interactable types. Build a synthetic door/button/control-room comparison first. The original article is a source of concepts; any third-party GOAP library needs its own current license review before integration.
